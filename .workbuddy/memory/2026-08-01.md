## 视频生成 400 "image URL could not be downloaded" 根因
- 报错：`video-submit HTTP 400 {code:invalid_request, message:"image URL could not be downloaded or did not return a valid supported image", data:{param:image}}`。
- 根因**不是代码 bug**：`PEA_EXTERNAL_REF_BASE_URL=https://720lp31wa108.vicp.fun/media`（花生壳子域）已**过期失效**。实测该子域（含任意 `/media/...` 路径）均返回「贝锐花生壳」HTML 占位页（HTTP 200, text/html），非用户服务器。Agnes 在公网下载到的是 HTML 而非图片 → 400。
- 链路本身正确：nginx `/media/`→`minio:9000/pea-media/`，`gen/` 匿名读策略 (`media_public_prefix=gen`) 配置无误，`_ensure_http_refs_for_video` 前缀拼接也正确（产出 `/media/gen/<key>` → 替换成 `https://<tunnel>/media/gen/<key>`）。

## `/api` 统一前缀重构（已上线）
- **触发**：用户问"为啥要加白名 nginx，每次加接口都要加？" —— 把这种易踩坑的设计彻底消灭。
- **架构**：
  1. **BFF**：`services/bff/src/main.ts` 加 `app.setGlobalPrefix('api')` —— 所有 controller 自动带 `/api` 前缀。BFF 镜像 baked-in，改完须 `docker compose build bff` + `up -d`。
  2. **nginx**：`infra/docker/nginx.conf` 用一条 `location /api/ { proxy_pass http://bff:4000; }`（**末尾不要带 `/`**，否则 nginx 会剥掉 `/api` 前缀，BFF 找不到路由）。
  3. **前端 axios**：`web/src/api/client.ts` 的 `baseURL='/api'`，所有 `api.get('/xxx')` 自动变成 `/api/xxx`，**不用改任何具体调用代码**。
  4. **前端直接 fetch**：`NodeChatPrompt.tsx` 的 `/chat/stream` → `/api/chat/stream`（绕过 baseURL，必须显式写）。
  5. **vite dev proxy**：`web/vite.config.ts` 用 `'/api': { target: 'http://127.0.0.1:4100', changeOrigin: true }` 一条覆盖所有。**不要写 `rewrite: (p) => p.replace(/^\/api/, '')`**，那会把 `/api` 剥掉。
- **验证**（managed python3.13 + playwright）：所有 API 调用都走 `/api/*` 前缀（`/api/users/me`、`/api/canvases`、`/api/billing/balance` 等），0 个 4xx/5xx，0 个 console error。
- **代价**：以后加新 controller 不用再动 nginx / vite proxy；BFF 改 main.ts 也只需 rebuild bff 镜像。
- **教训**：nginx `proxy_pass` 末尾的 `/` 是个隐形陷阱——会把 location 前缀剥掉，导致路径对不上。

## 参考图解析重构为显式 Strategy 模式（已上线验证）
- **用户疑问**:「图片生成是不是支持 base64? 怎么需要走公网? 弄成策略形式, 支持base64的直接传base64, 不行的才走公网」。
- **结论(已读源码确认)**: Agnes **图像**接口(`/v1/images/generations`, 参考图放 `extra_body.image[]`)**支持 base64 内联**; 只有**视频**接口的 `image` 字段只认 http(s) URL、不认 base64。所以图片生成本来就不走公网(内部 localhost 参考图经编排器 MinIO 直下转 base64 内联), 之前那次失败真因是 **prompt 触发 content_policy_violation**(少女/18岁/换装), 不是参考图走公网。(此前日志那条 "Agnes 访问不到 localhost" 是读了 DB 里原始 payload_json 推断的, 实际 image 路径会把 localhost 转 base64, 该推断不准确, 以本结论为准)
- **改动**(`services/generation-orchestrator/`):
  1. `app/param_adapters.py` 新增 `ReferenceResolutionStrategy`(ABC) + 两个实现:
     - `Base64InlineStrategy`(图片类): `data:` 原样保留; 内部/相对 URL 经 MinIO 直下转 base64; 公网 URL 原样保留。**不调 storage.store_bytes, 不经公网**。
     - `PublicUrlStrategy`(视频类): 先 `_normalize_refs` 转 base64, 再 `provider.resolve_refs(...)` 转存公开存储得公网 URL。
     - `ImageParamAdapter.ref_strategy` 默认 = `Base64InlineStrategy()`; `AgnesImageAdapter`/`GenericOpenAIImageAdapter` 显式声明 `Base64InlineStrategy`。
     - 新增 `_clean_ref_list`(仅基础规整, 不做 base64 转换); `normalize_image_params` 改为存 raw refs, 转换交由策略在 provider 层执行。
  2. `app/agnes_provider.py`: 图像生成(`_generate_image`/`_generate_image_async`)改为 `norm.reference_images = adapter.ref_strategy.resolve(norm.reference_images, self)`; 视频 `_build_video_payload` 改为 `PublicUrlStrategy().resolve(raw_refs, self)`。移除隐式 `_normalize_refs` 直接调用。
  3. 新增单测 `tests/test_ref_strategy.py`(8 例全过, 在重建后的容器内运行)。
- **部署**: 编排器镜像 baked, 改 `services/generation-orchestrator/**` 后 **必须** `docker compose up -d --build generation-orchestrator` 重建才固化(`docker cp` 仅临时)。
- **验证**: 容器内 `python /app/tests/test_ref_strategy.py` → 8/8 PASS; 端到端 smoke 确认 Agnes 图像 payload 把 `localhost:9000/pea-media/...` 参考图内联为 `data:image/png;base64,...`(未走公网)。
- **收益**: 以后加新模型 = 选 `Base64InlineStrategy` 或 `PublicUrlStrategy`(或自定义), 参考图解析逻辑不再散落; 图片生成彻底免公网配置。
