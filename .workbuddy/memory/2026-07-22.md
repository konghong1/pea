## pea 核心子系统详细设计（10 万用户量级）
- 用户要求把架构里"三重心+文件存储"按 ~10 万用户量级做详细设计，产出：`tapnow/DESIGN-Core-Subsystems-100k.md`，附生成管道时序图(Visualizer)。
- 容量模型假设：DAU 2万、日生成 ~6k(图85%/视频15%)、画布60GB、生成媒体~50TB(需生命周期)、ledger 年~440万行(按月分区)。
- 四大设计：
  1. 生成异步解耦：API 仅校验+预扣+返 jobId(<2s)，Worker 异步；队列优先级(极速/普通)+每用户限流+Provider 预算/断路器/回退；状态机 queued→running→done/failed→refunded；幂等 idempotency_key；视频 GPU worker 20–30、图像 10–15 并发池；失败补偿退还积分。
  2. 积分双记账本：accounts(balance,version 乐观锁) + ledger_entries(借贷两行,txn_id 唯一,按月分区)；预扣在事务内行锁完成；余额 Redis 缓存(Cache-Aside+单飞)；每日对账兜底。
  3. 画布自动保存：debounce 1s+失焦+beforeunload；PUT 带 version 乐观锁，409 冲突处理；canvases 表 JSONB + canvas_versions 历史；IndexedDB 离线草稿；Now 用整图版本号，协作(CRDT)进 Later。
  4. 文件存储：S3 兼容+预签名直传(用户图)+Worker SDK 写(产出)+CDN；key 前缀租户隔离；强制签名 URL 防跨用户泄露；生命周期(7天标准→30天IA→180天归档)控 50TB 成本；去重+缩略图+病毒扫描。
- 跨系统一致性：仅"预扣+退还"走强一致事务，其余事件+补偿最终一致。
- 开放问题：Temporal vs Celery、积分过期/隔离、离线 SLA、媒体配额、视频并发限额。

## pea Web 运行时真实验证（浏览器实跑，续上轮）
- 上轮只验证了后端三档(Orchestrator 14/14 + BFF 10/10) + Web 构建；Web 从未在浏览器真实跑过。本轮用 Playwright(托管 venv)驱动本机真实 Chrome 实跑 dev server(:5173)，再发现并修复 6 个真 bug（全静态漏）：
  1. **陈旧 dev server**：运行的 :5173 进程服务的是旧 Web 代码(`/api/auth/register`+`username` 字段)，与当前磁盘代码(`/auth/register`+`displayName`)不一致 → 浏览器注册 500。kill 旧进程、用当前源码重启。
  2. **BFF canvases.service.ts 双解包**：`const [r] = await this.db.query(...)` 但 `DatabaseService.query` 已解包（SELECT 返 rows/INSERT 返 OkPacket），导致 INSERT 后 `r` 为 undefined → `(undefined).insertId` 抛 500，`POST /canvases` 必崩。改为 `const r = await this.db.query(...)` 直接取 `r.insertId`/`r.affectedRows`（与 billing/auth 服务同一约定）。
  3. **BFF 重启丢宿主机 env**：`node dist/main.js` 用默认 `mysql`/`redis`(docker 服务名) → `getaddrinfo ENOTFOUND mysql`。补 `services/bff/.env`（宿主机用 localhost）并重起。
  4. **antd 静态 message 警告**：4 个组件用 `import { message }` 静态调用 → 控制台告警且丢失主题上下文。改为在 `<AntApp>` 内 `App.useApp()` 取 `message`（Inspector/CanvasEditor/Login/TopNav）。
  5. **favicon 404**：dev 无 favicon → 加内联 SVG favicon 到 index.html，控制台清零。
  6. **【最关键】WS 实时层完全失效**：BFF 日志 `ioredis ... Connection in subscriber mode, only subscriber commands may be used`。根因：`RedisPubSubService.onModuleInit` 在 subscriber 连接就绪前就 `subscribe()`，ioredis 随后发 `INFO` ready 检查被拒，连接永不 `ready`，`SUBSCRIBE` 永不发出 → 无人订阅 `pea:events` → 所有 WS 推送(job.updated/balance.changed)到不了前端。修复：subscribe 改到 subscriber `'ready'` 事件后执行；gateway 改经 `redis.onMessage(...)` 注册处理器。修复后 `pubsub_channels` 出现 `pea:events`，浏览器生成任务 `done` 且余额经 WS 实时更新(990)。
- 浏览器全链路验证通过：注册赠 1000 → 加生成节点/选节点/填提示词/⚡生成 → Orchestrator Worker 消费 → 前端经 WS 收到 `job.updated:done` + `balance.changed:990`，控制台零错误。
- 教训强化：**静态校验(py_compile/tsc/vite build/docker compose config)一个真 bug 都抓不到**；必须浏览器实跑"前端→dev proxy→BFF→Orchestrator→Redis→WS→前端"全链路，尤其 WS/事件订阅这类只运行时不报错的东西。e2e_bff.py 用 urllib 轮询 REST，没覆盖 WS，所以漏了 #6。
- 验证脚本沉淀：`scripts/web_smoke.py` `web_e2e.py` `web_capture.py` `web_diag.py` `web_gen.py`（Playwright + 本机 Chrome channel；**路径陷阱**：托管 Python 会把 `/d/workspace` 写成 `D:\d\workspace`，须用 `D:/workspace/...`）。
