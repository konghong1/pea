## 本会话：真实图"还是很慢"排查 + 解决（ADR-004）
用户原话："现在能出图了。还是很慢 排查下是什么原因。并给出解决"
- **根因（铁证日志）**：`[agnes] attempt 1 ReadTimeout (read timeout=110), retry in 4s` → `route() took 214.65s`。image 读取超时硬编码 110s < Agnes 峰值 100~170s → 慢但有效的响应被误杀→从头重试→延迟≈翻倍。配置 `PEA_PROVIDER_IMAGE_TIMEOUT_S=300` 与 worker 硬超时 330s 预算充足但 image 路径未用。
- **修复 `agnes_provider.py`**：① image 读取超时 `110`→`settings.provider_image_timeout_s`(300)，覆盖 Agnes 峰值，单次跑完不超时；② `_post_with_retry` 重试范围**移除 `requests.Timeout`**，只保留 429/500/502/503 + `ConnectionError`——读取超时=真挂死，重试只会把已等时间作废；Agnes 峰值延迟表现为「带 503 的响应」(5xx) 仍在 300s 内被接收并重试，语义不变。
- **固有下限（非架构可解）**：真实 Agnes flash 典型 18~77s、峰值 ~170s，无法压到 1~3s；本修复消灭的是"可避免的超时→重试翻倍"，把 ~214s 降回模型固有区间。
- **worker 并发提示**：`run_once` 单线程 `for` 串行（count=2 仅单次多取 2 条不并行）；单张图不受影响，多张会排队串行——后续若要并发可提 worker 并发，独立于本 ADR。
- 验证：`docker compose up -d --build generation-orchestrator` 生效；新建 `verify/timing_probe_real_image.py` 直接打 BFF 测真实出图端到端耗时（对照整改前 214.65s）。新增 `ADR-004-image-gen-timeout-retry-latency.md`。
- **附带坑**：`verify/timing_probe_real_image.py` 初版在 `POST /plans/purchase {"planId":"free"}` 收 400（plan "free" 非有效 id）；`call()` 改为不抛 HTTPError 后继续，生成仍成功（E2E 同理未断言 purchase）。

## 用户追问：为啥我直调 apihub.agnes-ai.com/v1 秒回，你们系统很慢？
- **同源对照实测**（同一台机器出口、同一把 key）结论：
  - 我们 pipeline 只加 ~2s（队列→worker→模型→回调→WS→节点），**不是瓶颈**。
  - 网络到 Agnes **仅 1.7s RTT**（connect 24ms / TLS 0.8s），**不是瓶颈**。
  - 慢的 100% 是**模型调用本身**：`agnes-image-2.0-flash`@2048² 固有 ~79s（系统端到端 94.9s）；图像扩散从本机出口根本做不到「秒回」。
  - 用户「秒回」几乎必然来自**不同调用**：更小尺寸(512/1024²) / 更快模型(2.1-flash) / 或调的是**文本端点 `/v1/chat/completions`**(首 token 秒回，与图像扩散不可比)。
- **已落地两项默认调整（质量换速度，可回退）**：
  1. 默认分辨率 `2k`→`1k`（`web/src/components/NodeChatPrompt.tsx` `useState('2k')`→`'1k'`，即 2048²→1024²）。
  2. 默认图像模型 `agnes-image-2.0-flash`→`agnes-image-2.1-flash`（`ai_models.is_default` 翻转，已 UPDATE 生效）。
  3. 预期默认出图从 ~95s 降到 30~50s 区间。web 已 rebuild + docker cp + nginx reload 生效。
- ADR-004 追加「默认模型与默认分辨率」决策段，记录上述对照实测与 trade-off。
- **诚实边界**：真实图像扩散物理下限仍在数十秒，架构压不到「秒回」；若用户坚持秒级，唯一出路是 Agnes 侧 turbo/极小模型，或接受其「秒回」实为文本端点。
