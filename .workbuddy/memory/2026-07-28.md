## 修复：图片/视频节点「尺寸选择框」4 个问题（NodeChatPrompt.tsx + PeaNode.tsx + styles/index.css）

根因与改动：
- **问题1（选比例后浮层立即关闭）**：`persistAspect` 里误加了 `setAspectOpen(false)`，导致点比例后尺寸框弹出，来不及选分辨率/时长/音频。已移除，浮层保持打开，由再次点击按钮/Esc/点空白关闭。
- **问题2（比例尺寸不统一）**：`PeaNode.tsx` 中 `MIN_HEIGHT=280` 把 16:9/21:9/4:3/3:2 等横屏比例都裁成 340×280，比例被悄悄改变。降至 140（21:9→146 不触发），让所有常规比例按真实宽高比渲染。另统一选择框内比例预览图标为固定 22px（图片/视频模式一致）。
- **问题3（视频框滚动条）**：视频 6 列比例网格中 svg 固定 28px 在 240px 面板内横向溢出；因 `overflow-y:auto` 使 `overflow-x` 计算值变 `auto`，出现横向滚动条。已将图标缩到 22px、按钮加 `min-width:0;overflow:hidden`、6 列 gap 降至 4px，并给 `.node-aspect-picker` 加 `overflow-x:hidden`、放宽 `max-height` 到 `calc(100vh-24px)`（仅极端矮屏才滚动）。
- **问题4（选择框不随节点移动）**：`aspectTriggerRect` 仅点击时取一次、固定定位不跟随。新增 `useAnchoredRect(open, ref)` hook：浮层打开期间每帧读取触发按钮实时 `getBoundingClientRect` 并更新坐标（静止不重渲），使浮层随节点拖拽/画布平移缩放无缝跟随。同时修改外部点击关闭逻辑：节点本体/输入栏(`.pea-node`/`.node-chat-prompt`)内点击不再关闭浮层，使其能在拖拽时跟随。模型/数量浮层也复用该 hook 保持一致。

验证：`tsc --noEmit` 通过；`vite build` 通过（仅既有 chunk 体积告警）。

注意：`.pea-node`/`.node-chat-prompt` 内点击不关闭浮层后，关闭方式改为：再次点击触发按钮 / 点击空白画布 / Esc。

## 问题2 的重新澄清与修正（用户追问）

用户对"尺寸不统一"的真实诉求：**比例里那个较大的数字（最长边）应恒为同一物理像素**。原第一版修复（仅降 MIN_HEIGHT）方向相反——它让横屏比例按真实比例渲染（高变矮），但竖屏比例的"大数字"仍是被算高的，与横屏同数字宽度不一致。
例：`9:16` 原 340×604（16=高=604），`16:9` 原 340×191（16=宽=340）→ "16" 大小不一。

**第二版修法（仍有白边）**：`PeaNode.tsx` 删除 `NODE_WIDTH`/`MIN_HEIGHT`，改为 `LONG_EDGE=340` 常量，按 `w>=h` 取长边为宽或高、短边按比例算，inline 写 `width/height` 给内层 body-card。这样 9:16→191×340、16:9→340×191，"16"均=340。但 `.pea-node` 外壳仍 340 宽，导致竖屏节点两侧出现白边（如 9:16、3:4 截图所示）。

**第三版（最终）修法**：把尺寸控制上提到**节点外壳**以消白边：
- `PeaNode.tsx` 计算出的 `nodeSize` 拆成两套样式：
  - `outerStyle` 注入 CSS 变量 `--pea-node-width: <width>px`
  - `bodyStyle` 只设 `height: <height>`，body-card 保持 `width:100%` 撑满外壳
- `.pea-node` 的 `width` 改为 `var(--pea-node-width, 340px) !important`
这样 9:16 整个节点变为 191×340，body-card 宽度=191、无白边；16:9 为 340×191。最长边仍恒为 340，"16"一致。Prompt 输入栏是 520px 绝对定位居中，不受节点宽度限制。
已用脚本核验全部比例最长边均=340。
（仅作用于空白/占位节点；有内容后 `hasMediaContent` 不注入变量，走 `aspect-ratio:auto` 按实际媒体包裹，不受影响。）

## 问题4（@图片发送后生成图与参考图无关）后端根因定位 + 修复

前端侧此前已修（NodePromptInput：缩略图刷新、resolveNodeMediaUrl 优先 getFileUrl、getParsed 过滤 blob:；NodeChatPrompt：解锁模型才能 submit）。但编排器日志仍有 `[refs] dropped 1 unreachable reference image(s)` → 参考图被静默丢弃，生成图不参考原图。

**真根因（与"localhost 指向自身"旧假设无关）**：编排器容器内 MinIO 客户端本就配 `minio:9000`（docker-compose PEA_MINIO_ENDPOINT），`_resolve_internal_ref_via_minio` 也不按 URL host 下载、而是用自有客户端按提取的 key `get_object`。问题在 **key 编码错位**：
- 上传对象以字面 key 存储：`u:594/uploads/xxx.png`（冒号是字面 `:`）。
- BFF 生成的签名 GET URL 路径把 `:` 编码成 `u%3A594/...`。
- 旧 `_extract_minio_key_from_url` 未做 `unquote`，返回编码 key `u%3A594/...` → `get_object` → `NoSuchKey` → 丢弃。
- 容器内运行的是**未含 unquote 修复的旧镜像**（orchestrator 用 `build:` 无 volume 挂载，源码改了但容器没重建），故 E2E 一直复现 dropped。

**修复**：
1. `services/generation-orchestrator/app/param_adapters.py` 的 `_extract_minio_key_from_url` 已含 `unquote`（磁盘源码正确）。
2. 增强 `_resolve_internal_ref_via_minio`：对提取 key 同时尝试「解码后」(`u:594/...`) 与「原样」(`u%3A594/...`) 两种候选，任一命中即转 base64，避免编码约定差异导致 NoSuchKey。
3. **关键**：`docker compose up -d --build generation-orchestrator` 重建镜像让运行容器吃上新代码（Dockerfile 源码 COPY 在 pip install 之后，源码改动会使该层失效重拷）。

**验证**：
- 容器内单测诊断：用编排器自有 `_get_client` 上传 `u:594/...`、构造与 BFF 一致的签名 URL（minio:9000→localhost:9000），`_normalize_refs([url])` 现返回 resolved（不再 dropped）。
- 容器内走完整生产路径：`normalize_image_params` → `reference_images=[data:image/png;base64,...]`；`AgnesImageAdapter.build` → `extra_body.image=[data:...]`（参考图确实进入模型请求体）。
- E2E `verify/verify_ref_issues.py` 全绿（4 项问题全过），`/generation/node` 请求 `reference_images=['http://localhost:9000/pea-media/u%3A594/uploads/...?X-Amz-...']`；对应实时 job `status=done`，resultUrl 为 Agnes `/i2i/` 真实出图（图生图，证明参考图被模型消费）。

**经验**：Python 服务改源码后必须重建镜像（非 volume），否则运行容器仍是旧代码，E2E 会持续复现"已修复"的 bug。诊断用 `docker cp` 到容器 `/app` 再 `python` 跑，比在宿主机猜更权威。
