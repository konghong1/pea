## 根因排查：fetch remote models failed: ECONNREFUSED 172.17.0.1:33210

- 报错文案 `fetch remote models failed:` 来自 **pea BFF**（`services/bff/src/modules/providers/providers.service.ts:207`），不是 ai-agent。BFF 拉 `/v1/models` 时经 `bootstrap-proxy.ts` 的 `EnvHttpProxyAgent` 强制走 `HTTPS_PROXY` 代理，代理地址 `172.17.0.1:33210` 连不上 → ECONNREFUSED。
- 根因：`172.17.0.1` 是 **Linux 专属** Docker 网桥网关；**Windows Docker Desktop 没有 docker0**，容器访宿主机须用 `host.docker.internal`。该坏配置不在仓库里（grep 全无），只可能来自用户本地 env / 自建 `docker-compose.override.yml` / `.env` 的 `HTTPS_PROXY` 或 `PEA_EGRESS_PROXY`（疑似从 Linux 迁 Windows 未改）。
- 代理还须绑 `0.0.0.0`（非 `127.0.0.1`）且进程在跑，容器才能经网桥接口访问。
- **差异点（重要）**：ai-agent(Python) 有 `app/http_client.py:ensure_proxy_strategy()` 启动探测代理、连不上自动清空 proxy 走直连；pea BFF `bootstrap-proxy.ts` 无条件装 `EnvHttpProxyAgent`、无兜底 → 代理挂则全死。这正是“ai-agent 能、BFF 不行”的原因。
- 方案：① 撤代理走直连（不需代理时最快，B）；② `PEA_PROXY_FIX=1`+`PEA_EGRESS_PROXY=http://host.docker.internal:33210` 且代理绑 0.0.0.0（A，符合项目设计）；③ 给 BFF 加同款代理兜底（C，长期加固）。

## 已实施修复（用户要“一定可行”方案，直接落地 C）

- 已改 `services/bff/src/common/proxy/bootstrap-proxy.ts`：`installEgressProxyFromEnv` 改为 async，新增 `isProxyReachable()` TCP 探测（2s 超时）；代理不可达时**跳过安装、退回直连**，镜像 ai-agent 的 `ensure_proxy_strategy()`。main.ts 调用处未 await，无副作用。
- 效果：无论 BFF 环境里有没有坏代理 `172.17.0.1:33210`，都自动直连出网拉模型，与 ai-agent 行为一致。落地方式：服务器上 `docker compose up -d --build bff`（永久）或移除 `PEA_PROXY_FIX`/`PEA_EGRESS_PROXY`/`HTTPS_PROXY` 后 `restart bff`（即时）。
- 结论重申：pea 从不需要代理，之前崩是被死代理 `172.17.0.1:33210` 强制路由；ai-agent 能跑是因有“坏代理就直连”兜底。现已补齐。

## 部署配置最终决策（用户追问 PEA_DNS_FIX / PEA_PROXY_FIX 是否必要）

- `PEA_PROXY_FIX` → **设 `0`**。它（经 `proxy-override.yml` 注入 `HTTPS_PROXY=...:33210`）是 `ECONNREFUSED` 的直接元凶；代理没在跑。BFF 现已带直连兜底，代理彻底不需要。服务器的 `.env`（不在本 Windows 工作区，在部署机上）改 `PEA_PROXY_FIX=1` → `0` 后 `./start.sh --build` 重建。

- 工作区无 `.env` 文件：用户贴的 `.env` 配置位于 Linux 部署机，本地 Windows 仅代码仓库，无法在此直接改。

## ⚠️ 重大修正：172.17.0.1:33210 是 AI 服务商 base_url，不是 HTTP 代理！

## ⚠️ fetch-models 根因最终定案（2026-07-29 14:30，读 ai-agent 源码后纠正全部旧推断）

- **读 `D:\workspace\ai-agent` 源码得到的铁证**（非推断）：
  - `app/agent.py:176` 注释：`ai-agent 容器被注入 HTTPS_PROXY=host.docker.internal:33210`，33210 是**宿主侧 HTTP 转发代理**，**不是 API 地址**。

## ⚠️ 15:15 代码定案：报错 172.17.0.1 来自容器 env 的 PEA_AI_GATEWAY，非默认值

## 🔴 15:48 canvas 创建 500：FK fk_canvases_owner 失败（stale JWT）

- 报错：`DB error: Cannot add or update a child row: a foreign key constraint fails (pea.canvases, CONSTRAINT fk_canvases_owner ... REFERENCES users(id))`，路径 `/canvases`，ts 07:44。
- **根因（代码级）**：`canvases.owner_id` 直接来自 JWT `sub`（`canvases.controller.ts:34` → `canvases.service.ts:43` `INSERT INTO canvases (owner_id,...) - **立即修复（用户侧，零风险）**：浏览器**退出登录→重新登录**，按当前库真实 `users.id` 签发新 token，sub 对得上，建画布即通（admin: admin@pea.ai / konghong）。

- **通用教训**：凡是 `docker volume rm` 重建 MySQL，所有已登录用户的 JWT 即刻失效（sub 指向旧 id）。要么让用户重登，要么守卫做用户存在性校验（本项目已加）。
