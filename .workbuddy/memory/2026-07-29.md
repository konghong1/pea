## 排查: 管理员"拉取模型"失败 (fetchRemoteModels)
- 链路: `POST /admin/providers/:id/fetch-models` → `providers.service.fetchRemoteModels` → `GET {base_url 去尾/v1}/v1/models`, 取 `data.data`, 落 `provider_remote_models`。`normalizeModelsUrl` 写死拼 `/v1/models`。
- **根因(大概率)**: 默认 Agnes 提供商是图像/视频生成 API, 只有 `/v1/images`、`/v1/videos` 任务端点, **没有 `/v1/models` 列表接口** → 拉取必 404/报错。Agnes 模型由 dbmigrate 直接 seed 进 `ai_models`, 无需拉取。该失败**不影响真实出图/出视频**(生成走 seed 的 ai_models)。
- 若用户配的是别的 OpenAI 兼容提供商(OpenAI/OpenRouter/LiteLLM), 失败常见: 容器无公网 egress / base_url 未到 /v1 级 / 响应非 OpenAI 形状 `{data:[...]}` / key 无效401。
- 诊断命令: `docker compose exec bff curl -s -o /dev/null -w "%{http_code}" -H "Authorization: Bearer <key>" <base>/v1/models`。
- 改进建议(未做): fetchRemoteModels 对无 models 接口的提供商应返回 `{models:[], note}` 而非抛错。待用户确认是否改。
- **用户实测确认**: 浏览器控制台 `POST http://106.54.88.67:8088/admin/providers/agnes/fetch-models 400 (Bad Request)` 坐实根因。精确 URL = `GET https://apihub.agnes-ai.com/v1/models`(normalizeModelsUrl 去尾/v1 再拼回, 单一 /v1/models 正确)。400 即 catch 内 `BadRequestException('fetch remote models failed: <detail>')`, detail 为上游真身。
- **【重要更正】用户强调"本地同配置能拉到"** → 证明 `apihub.agnes-ai.com/v1/models` 端点真实存在且返回 200。故前述"agnes 无 /v1/models 接口"推断**错误**(系误将视频报告里 /v1/images,/v1/videos 的 404 外推)。Linux 上 400 的真正原因是**服务器到 apihub 的网络不可达**(区域限制/DNS污染/需代理未配/容器CA证书旧), 属环境差异非代码差异。这同时会影响真实生成(orchestrator→agnes)。诊断: 在 Linux 上 `docker compose exec bff curl apihub /v1/models`、宿主机直连、`nslookup` 看 DNS; 并查 400 响应 body 的 `<detail>` 文本(含 ENOTFOUND/ETIMEDOUT/certificate 等真因)。待用户给诊断结果再给精确改法(代理 env / CA certs / DNS)。
- **【实锤·同源】bff 容器日志末尾**: `WARN [ChatService] chat stream failed, refunding txn ...: LLM upstream unreachable: fetch failed`。这与 fetch-models 400 同源=**bff 容器出不了公网到外部 AI 接口**(undici `fetch failed`=DNS/连接层失败)。结论: 本地能通(用户网络/VPN)、Linux 不通, 确定是服务器/容器出网问题; 且所有外部 AI 功能(chat/拉模型/出图出视频)在 Linux 均会因此挂。诊断命令已给(容器内 curl + 宿主机 curl + nslookup, 看 `errormsg`)。关键修复点: 若需代理, bff 的 axios 与 undici fetch **默认均不读 HTTP_PROXY env**, 须代码同时挂代理(axios.proxy / undici ProxyAgent); orchestrator(Python)会自动读 env。
- **注意**: Nest 日志只打印外层 `fetch failed`, **不含底层 cause**(undici 吞掉), 看容器日志定位不到真因, 必须主动探测。bff=node:20-alpine 可能无 curl, 改用 `docker exec <bff> node -e "fetch(...).then(r=>...).catch(e=>console.log(e.cause?.code||e.cause?.message))"` 复现并取 `e.cause`(ENOTFOUND=DNS / ETIMEDOUT=出网需代理 / certificate=CA旧)。待用户给 `ERR` 输出再定改法。
- **【根因实锤·DNS 污染】** 用户在 Linux 服务器 `ping apihub.agnes-ai.com` 解析到 `69.171.247.32`(69.171.x.x 属 Meta/Facebook, 非 apihub 真实服务器) → 典型 **DNS 污染/劫持**。bff/orchestrator 用被污染 DNS 连到假 IP → fetch failed → fetch-models 400 / chat 失败。本地能通是因本地(或 VPN/代理)解析到真实 IP。结论: 非代码/非"agnes 无接口", 是服务器 DNS 把境外域名指错。修复方向(待用户给本地真实 IP): ① compose 给 bff+orchestrator 加 `extra_hosts: ["apihub.agnes-ai.com:<真实IP>"]` 绕过污染(最稳, web 不需加); ② 或配干净 DNS 解析器(国内直连境外 DNS 常被污染, 可靠性差); ③ 或走 HTTPS_PROXY(需代码接 axios+undici)。需用户本地 `nslookup apihub.agnes-ai.com` 取真实 IP 后再改。
- **用户追问"本地能拉到、Linux 不能"**: 强调代码确定性——同一 provider 配置在任何机器请求一致, 无"本地特例"。差异只可能两来源: ① 本地拉的是别的 OpenAI 兼容 provider(支持 /v1/models), Linux 测的是 agnes(天生不支持); ② 本地 agnes 的 base_url 指向实现了 /v1/models 的网关/本地代理。验证法: 两端 `SELECT id,base_url FROM ai_providers;` 对比。真实 agnes 两端均 400, 设计如此。

## 【根因补全】同服务器 ai-agent 能通、pea 不通 = 沙箱出口代理
- 用户对质："同一服务器、同一 apihub 地址，前次部署(ai-agent)能拉到，pea 拉不到"。
- 查 `D:\workspace\ai-agent\docker\docker-compose.yml` 与 `app/http_client.py` 坐实：ai-agent 的 api/worker 容器设了
  `extra_hosts: host.docker.internal:host-gateway` + `HTTPS_PROXY/HTTP_PROXY: http://host.docker.internal:33210` + `NO_PROXY`。
  注释明写 "host WorkBuddy sandbox proxy"——即服务器上有一个**宿主机出口代理在 33210**，它用干净 DNS 解析 apihub 再转发，绕开污染。
  ai-agent 是 Python，requests/httpx/openai **默认读 HTTPS_PROXY env**，零代码生效。
- pea 没有任何代理配置 + bff=Node(axios/undici 默认不读代理 env) → 容器直连被污染 DNS → fetch failed/400。
- **结论**：差别正是"ai-agent 走了那个沙箱代理、pea 没走"，非代码差异。
- **pea 修法决策**：不推荐照搬代理方案（依赖 33210 代理还在跑 + bff 需改 axios/undici 代理代码）。初版用 `extra_hosts` 写死单 IP，但用户两次 `nslookup` 返回不同 IP(74.86.228.110 / 108.160.170.44)= apihub 是多 A 记录/CDN 轮询, 写死单 IP 是单点且会过时。**最终升级为给 bff+orchestrator 指定干净公共 DNS(223.5.5.5 阿里 / 119.29.29.29 腾讯)**, 容器自动解析真实 IP 且支持多 IP 轮询; 对 Python/Node 均零代码生效。

## 【已修复】DNS 污染 → 可选 DNS 修复 overlay (非强制)
- 根因：服务器递归解析器把 `apihub.agnes-ai.com` 污染指向假 IP `69.171.247.32`(Meta)。用户本地 30+ 次 `nslookup` 经 AliDNS 返回真实 IPv4 `118.193.202.219` / `162.125.7.1` 轮询、IPv6 `2001::629f:6c3a`/`2001::76c1:cadb` → **确认 apihub 是多节点/CDN 集群, 真实 IP 不止一个 (之前写死单 IP 74.86/108.x 不稳健)**。
- **方案演进**：① `extra_hosts` 写死单 IP → 因多 IP 轮询/会过时弃用；② 硬编码 `dns:[阿里,腾讯]` 于主 compose → 用户指出"干净环境本就能访问, 不应强制"；③ **最终改为可选 overlay**：主 compose 移除 dns(默认走宿主 DNS, 完全不强制)；新建 `docker-compose.dns-override.yml` 仅给 bff/orchestrator 加干净公共 DNS(223.5.5.5/119.29.29.29)；`start.sh` 加载 `.env` 的 `PEA_DNS_FIX`(默认1=开, 设0=关) 决定是否 `-f` 叠加 overlay。
- 行为：污染服务器(默认 PEA_DNS_FIX=1)开箱即用叠加干净 DNS；干净环境(本地/正常服务器)在 .env 设 `PEA_DNS_FIX=0` 即走宿主默认解析, 零干预, 不强制。
- Docker 内建 DNS(127.0.0.11) 仍优先处理服务名(bff/mysql 等), overlay 的 dns 仅影响外部域名解析 → 不影响容器间通信, 也不影响新增其他 provider(反而可能更通)。
- 校验: YAML 主/overlay 通过; `bash -n start.sh` 通过。
- 验证: 叠加时 `docker compose exec bff getent hosts apihub.agnes-ai.com` 应返真实 IP; `node -e fetch(...)` 不再 `fetch failed`。
- 用户曾误想用云厂商"添加域名解析"面板改 `agnes-ai.com→服务器IP` —— 已否定(不拥有该域名/不影响递归解析链路)。
- **【待服务器实测】已生成 `pea-server/.env`(gitignored, 含随机强口令 + `PEA_DNS_FIX=1`)**。该文件不进 git, 部署到服务器需手动 `scp` 或 `cp .env.example .env` 重建。DNS 修复是**运行时配置**, 必须在服务器重建 bff/orchestrator 容器才生效(`./start.sh --down && ./start.sh -d` 或 `docker compose -f docker-compose.yml -f docker-compose.dns-override.yml up -d`)。若叠加后仍 `fetch failed`, 兜底改 `dns-override.yml` 为 `extra_hosts: ["apihub.agnes-ai.com:<本地 nslookup 实时 IP>"]`(取 118.193.202.219/162.125.7.1 之一)。

## 【已按用户要求改】overlay 由"纯干净 DNS"升级为"extra_hosts 固定 IP + 干净 DNS"双保险
- 用户明确要把 apihub 写死成他本地 nslookup 得到的真实集群 IP(而非仅靠干净 DNS 解析)。故把 `docker-compose.dns-override.yml` 的 `bff`/`generation-orchestrator` 改为: 保留 `dns:[223.5.5.5,119.29.29.29]`(其它外部域名也救活) + 新增 `extra_hosts`(长语法 `host:/ip:` 以兼容 IPv6 冒号) 把 `apihub.agnes-ai.com` 写死 4 个 IP:
  - IPv4: `118.193.202.219`, `162.125.7.1`
  - IPv6: `2001::629f:6c3a`, `2001::76c1:cadb`
- 原理: Linux 解析顺序 `/etc/hosts` > DNS, `extra_hosts` 写入容器 `/etc/hosts` 优先级最高 → apihub 必命中真实 IP, 彻底绕过污染。
- 保留 `dns:` 的理由: 零副作用且让其它外部域名也走干净解析; 若用户只要纯 extra_hosts 可删两处 `dns:`。
- 注意点: ① 这些 CDN IP 可能随厂商调度变化, 失效需重 nslookup 覆盖; ② 容器默认 bridge 常无 IPv6 出口, 若 IPv6 报 network unreachable 删两条 IPv6 extra_hosts 即可(undici/Python 有 Happy Eyeballs 回落 IPv4); ③ start.sh 经 `PEA_DNS_FIX=1`(已确认 .env 设 1)自动叠加本 overlay。
- 验证命令(服务器): `docker compose exec bff grep apihub /etc/hosts` 应见 4 行; `node -e fetch('https://apihub.agnes-ai.com/v1/models',{headers:{Authorization:'Bearer x'}}).then(r=>console.log('HTTP',r.status)).catch(e=>console.log('ERR',e.cause?.code||e.message))` 不再 fetch failed。
