# 2026-07-29

## 根因排查：fetch remote models failed: ECONNREFUSED 172.17.0.1:33210

- 报错文案 `fetch remote models failed:` 来自 **pea BFF**（`services/bff/src/modules/providers/providers.service.ts:207`），不是 ai-agent。BFF 拉 `/v1/models` 时经 `bootstrap-proxy.ts` 的 `EnvHttpProxyAgent` 强制走 `HTTPS_PROXY` 代理，代理地址 `172.17.0.1:33210` 连不上 → ECONNREFUSED。
- 根因：`172.17.0.1` 是 **Linux 专属** Docker 网桥网关；**Windows Docker Desktop 没有 docker0**，容器访宿主机须用 `host.docker.internal`。该坏配置不在仓库里（grep 全无），只可能来自用户本地 env / 自建 `docker-compose.override.yml` / `.env` 的 `HTTPS_PROXY` 或 `PEA_EGRESS_PROXY`（疑似从 Linux 迁 Windows 未改）。
- 代理还须绑 `0.0.0.0`（非 `127.0.0.1`）且进程在跑，容器才能经网桥接口访问。
- **差异点（重要）**：ai-agent(Python) 有 `app/http_client.py:ensure_proxy_strategy()` 启动探测代理、连不上自动清空 proxy 走直连；pea BFF `bootstrap-proxy.ts` 无条件装 `EnvHttpProxyAgent`、无兜底 → 代理挂则全死。这正是“ai-agent 能、BFF 不行”的原因。
- 方案：① 撤代理走直连（不需代理时最快，B）；② `PEA_PROXY_FIX=1`+`PEA_EGRESS_PROXY=http://host.docker.internal:33210` 且代理绑 0.0.0.0（A，符合项目设计）；③ 给 BFF 加同款代理兜底（C，长期加固）。

## 已实施修复（用户要“一定可行”方案，直接落地 C）

- 已改 `services/bff/src/common/proxy/bootstrap-proxy.ts`：`installEgressProxyFromEnv` 改为 async，新增 `isProxyReachable()` TCP 探测（2s 超时）；代理不可达时**跳过安装、退回直连**，镜像 ai-agent 的 `ensure_proxy_strategy()`。main.ts 调用处未 await，无副作用。
- 效果：无论 BFF 环境里有没有坏代理 `172.17.0.1:33210`，都自动直连出网拉模型，与 ai-agent 行为一致。落地方式：服务器上 `docker compose up -d --build bff`（永久）或移除 `PEA_PROXY_FIX`/`PEA_EGRESS_PROXY`/`HTTPS_PROXY` 后 `restart bff`（即时）。
- 结论重申：pea 从不需要代理，之前崩是被死代理 `172.17.0.1:33210` 强制路由；ai-agent 能跑是因有“坏代理就直连”兜底。现已补齐。

## 部署配置最终决策（用户追问 PEA_DNS_FIX / PEA_PROXY_FIX 是否必要）

- `PEA_PROXY_FIX` → **设 `0`**。它（经 `proxy-override.yml` 注入 `HTTPS_PROXY=...:33210`）是 `ECONNREFUSED` 的直接元凶；代理没在跑。BFF 现已带直连兜底，代理彻底不需要。服务器的 `.env`（不在本 Windows 工作区，在部署机上）改 `PEA_PROXY_FIX=1` → `0` 后 `./start.sh --build` 重建。
- `PEA_DNS_FIX` → **保持 `1`**。与崩溃无关（报错是连代理被拒非 DNS 失败）；它是容器 DNS 防污染安全网，无污染时用干净 DNS 无害，留着更稳。仅在确认容器直连外部 AI 域名解析全正常时才考虑设 `0`。
- 工作区无 `.env` 文件：用户贴的 `.env` 配置位于 Linux 部署机，本地 Windows 仅代码仓库，无法在此直接改。

## ⚠️ 重大修正：172.17.0.1:33210 是 AI 服务商 base_url，不是 HTTP 代理！

- 之前"代理导致 ECONNREFUSED"的判断**错误**。真因是 Docker 网络可达性：
  - `fetchRemoteModels`(`providers.service.ts:198`)用 `axios.get(url)`,`url=normalizeModelsUrl(p.base_url)`=`${base_url}/v1/models`。所以报错里的 `172.17.0.1:33210` 是**provider 的 base_url 本身(目标地址)**，不是 HTTPS_PROXY。
  - bff 用 **axios ^1.7.7**，v1 **不读** `HTTPS_PROXY` 环境变量(这是 v0 行为，v1 已移除)。`bootstrap-proxy.ts` 折腾的 `globalThis.fetch`/undici 对这条 axios 路径**完全无效**。`bootstrap-proxy.ts:16` 的注释("axios 会自动读 env 走代理")是针对 v0 的过时错误认知。
  - `172.17.0.1` 是 docker0(默认网桥)网关，仅跑在**默认网桥**上的容器(ai-agent 大概率是)才到得了；bff 跑在 docker-compose **用户自定义网桥**上，`172.17.0.1` 对它不可路由 → ECONNREFUSED。这就是"ai-agent 能、bff 不行"的真正原因。
  - 用户加 `PEA_PROXY_FIX`(HTTP 代理)是南辕北辙：既改不了 axios 目标地址，axios v1 也不认该 env。
- 修复(已落代码):
  1. `docker-compose.yml` 的 `bff` 与 `generation-orchestrator` 服务加 `extra_hosts: [ "host.docker.internal:host-gateway" ]`，使容器内 `host.docker.internal` 恒解析到宿主(不再依赖 `PEA_PROXY_FIX` 的 proxy-override.yml)。
  2. 部署机动作：`.env` 设 `PEA_PROXY_FIX=0`(删死代理)；**把 pea AI 提供商的 base_url 由 `http://172.17.0.1:33210` 改为 `http://host.docker.internal:33210`**(在 pea 管理 UI / `ai_providers.base_url` 改)；`./start.sh --build` 重建。
  3. 验证：`docker compose exec bff curl -sS http://host.docker.internal:33210/v1/models` 应通。
- 结论重申：根因是容器网络隔离导致 bff 够不到宿主侧网关，与"是否需要代理"无关。用 `host.docker.internal` 走 host-gateway 即与 ai-agent 同路。

## 覆盖确认：fetch-models(400) 与 chat(LLM upstream unreachable: fetch failed) 同源，一并解决

- 用户再报 chat 生成时 `LLM upstream unreachable: fetch failed` 退款。该报错与 fetch-models 是**同一根因**：orchestrator 同样读 `ai_providers.base_url` 直连宿主侧 `33210` 网关，因用户网桥不可达 `172.17.0.1` 而失败。`host.docker.internal` + extra_hosts 已覆盖 orchestrator，故两错同修。
- 浏览器 Network 面板 `Remote Address: 127.0.0.1:33210` 是**用户本机浏览器本地代理(Clash 等)**，属客户端侧、与服务器报错无关；服务器回了 400 已证明 browser→server 通路正常。勿在此处纠缠。
- 唯一残余风险：若宿主 `33210` 网关只绑 `127.0.0.1`(未绑 `0.0.0.0`)，则 `host-gateway`(网桥网关 IP) 仍到不了它。验证：`ss -tlnp | grep 33210` 须见 `0.0.0.0:33210` 或含网关 IP；否则改绑 `0.0.0.0`。
- 部署机三步：① base_url `172.17.0.1`→`host.docker.internal`；② `.env` `PEA_PROXY_FIX=0`；③ `docker compose up -d --build bff generation-orchestrator`。

## ⚠️ docker-compose schema 坑（2026-07-29 修复）

- 给 bff 加 `PEA_AI_GATEWAY` 时误写到**服务顶层**(与 `ports:`/`extra_hosts:` 平级)，触发 `services.bff additional properties 'PEA_AI_GATEWAY' not allowed`。这是 Compose schema 校验报错，**与 Windows/Linux 平台无关**，任何系统都会拒；ai-agent 没出现只因它没有这个错位的 key。
- 修复：移入 `environment:` 块内(6 空格缩进)。`docker compose config -q` 返回 EXIT=0 验证通过。
- 真正的平台差异只有：`host.docker.internal` 在 Win/Mac Docker Desktop 自带，Linux 需 `extra_hosts: host.docker.internal:host-gateway`——与本次 schema 报错是两码事。

## ⚠️ 本地 `docker compose up` 卡在 dbmigrate exit 1（2026-07-29，已亲手修复）

- 现象：`Container pea-server-dbmigrate-1 Error service "dbmigrate" didn't complete successfully: exit 1`，bff/orchestrator 起不来。
- **真因（纠正，之前误判为"半初始化卷/缺表 1146"）**：日志实为 `ERROR 1045 (28000): Access denied for user 'root'@'172.19.0.5'`。
  - `.env` 里 `PEA_DB_ROOT_PASSWORD` 设了非默认值（如 `uW-YUIDNOv8Qx9WdA2YvBg`，Jul 29 11:23 改的）。
  - `mysql_data` 卷是**更早**建的，MySQL 只在**首次建卷**时用 `MYSQL_ROOT_PASSWORD` 初始化一次，该卷挂上后密码**锁死在旧值**。
  - 改 `.env` 密码后：MySQL 容器启动时**忽略新密码**（卷已存在），数据库里 root 仍是旧密码；dbmigrate 用 `.env` 新密码去连 → Access denied → exit 1。
  - mysql 服务与 dbmigrate 都读同一个 `PEA_DB_ROOT_PASSWORD`（compose line 16 / 63），配置一致；分歧只发生在「卷里存的密码 vs 现在 env 的密码」。
- 修复(确定性，已执行)：`docker compose down` → `docker volume rm -f pea-server_mysql_data` → `docker compose up --build -d`。清卷后 MySQL 按当前 `.env` 密码重初始化，dbmigrate 同密码连上 → 退出码 0、日志 `all assertions passed`。数据由 `01-schema.sql`+`assert-migrated.sh` 重建(admin/providers/plans 全在)，本地开发无损失。
- **复用教训**：改 `.env` 的 `PEA_DB_ROOT_PASSWORD` / `PEA_DB_PASSWORD` 后，必须同时 `docker volume rm pea-server_mysql_data` 重建卷，否则 dbmigrate 必 Access denied。这是"named volume 密码锁死"陷阱，不是缺表。
- 诊断(若仍失败)：`docker compose logs dbmigrate --tail 50`；`1045 Access denied`=密码锁死→清卷；`1146 table doesn't exist`=卷半初始化→也清卷；`1060 Duplicate column`=脚本真 bug→改 `assert-migrated.sh`。
- 验证结果（本次）：dbmigrate exit 0、all assertions passed；`docker compose ps` 全 Up/healthy；`curl localhost:8088` → HTTP 200。
