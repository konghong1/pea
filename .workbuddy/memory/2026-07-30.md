### 问题1：选区框在浅色背景下不可见
- **根因**：`.react-flow__selection` / `.react-flow__nodesselection-rect` 的 `background: rgba(31,162,220, 0.06)` 透明度太低（仅6%），在白色/浅色画布背景上几乎不可见；边框仅1px也不够明显。

### 问题2：打组后按 Delete 键白屏崩溃
- **根因**：`removeNode()` 删除组节点时，未清理子节点的 `parentNode` 引用。子节点仍持有 `parentNode: <已删除groupId>` + `extent: 'parent'`，ReactFlow 渲染时按 parentNode 查父节点找不到 → 抛异常/白屏。
- **修复**（`web/src/store/canvas.ts` `removeNode`）：
  - 检测目标节点是否为 `type: 'group'`，若是则从 `data.childrenIds` 收集子节点ID一并删除；
  - 额外防御：扫描所有 `parentNode === id` 的孤立子节点（防止 childrenIds 漏记）；
  - 用 `Set` 一次性批量删除，避免中间态崩溃。

### 附带修复：键盘 Delete 多选行为统一
- **问题**：键盘 Delete 只删单个 `selectedId`，多选状态按 Delete 只删一个节点（与工具条"删除全部"不一致）。
- **修复**（`web/src/components/CanvasEditor.tsx` 键盘监听）：当 `selectedIds.length > 1` 时，遍历删除所有选中节点。

## 新功能：画布撤销 / 重做（Ctrl+Z / Ctrl+Shift+Z / Ctrl+Y）
- **需求**：删除或做了操作后无法用 Ctrl+Z 撤销，需补全历史能力。
- **方案**：在 `useCanvas`(zustand) store 内加基于快照的历史栈（`past`/`future`/`takeSnapshot`/`undo`/`redo`）。
  - 每次「已提交的结构性变更」前调 `takeSnapshot()` 记录快照（最小可还原字段，与 `openCanvas`/`cleanGraph` 同口径，不含 ReactFlow 运行时字段）。
  - 覆盖动作：增/删节点(含批量 `removeNodes` 单条撤销项)、连线、复制、粘贴、打组、解组、组内重排、多选插入、编辑节点数据(`updateNodeData`)、删边。
  - **拖拽快照关键坑**：`onNodeDragStart` 在 mousedown 即触发(纯点击也触发)，放那会为每次点击产生无意义撤销项 → 改为在 `onNodesChange` 收到首个 `dragging===true` 的 position change 时记快照，一次拖拽=单条撤销项；`dragging===false` 时复位标记。
  - **编辑合并**：`updateNodeData` 传 label `'node-data:'+id`，同节点连续编辑(逐字输入)合并为单条撤销项，不同节点互不吞撤销项；idle/其它操作打断合并链。
  - **排除生成回写**：`applyJobResult`/`reconcileGeneratingNodes` 及 `nodeGeneration` 的 retry 写(`updateNodeData(...,false)`) 走 set 直写、不调 takeSnapshot → 生成中/生成结果不污染历史。
  - `openCanvas`/`loadGraph` 重置历史栈。
- **交互**：`CanvasEditor` 键盘监听接 Ctrl+Z(撤销)/Ctrl+Shift+Z 与 Ctrl+Y(重做)；焦点在输入框/contentEditable 时放行浏览器原生撤销；历史为空时 toast 提示。快捷键帮助文本已更新。
- **验证**：`tsc -b` 与 `vite build` 均通过(3272 模块)。`window.__canvas.getState().undo()/redo()` 在 dev 下可手动验证。

## 选区覆盖层 z-index + 屏幕坐标改造（用户又一轮反馈：覆盖层被压在节点后面、节点没选中）
用户反馈：`SelectionOverlay` 的填充「半透明在节点后面」露出边角（实际是 z-index 35 被 ReactFlow 内部 `.react-flow__viewport`/`.react-flow__nodesselection` 的 transform stacking context 压低），且「放开后一个节点都没选中」。headless E2E 15/15 PASS 复现不到，但用户真实浏览器有差。
- **z-index 9999 + isolation:isolate**：`pea-selection-overlay` 拉到 `z-index:9999` + `isolation:isolate`，确保覆盖层在所有 transform 容器之上（不会被 RF 内部 stacking context 压到节点背后）。`background` 从 0.10 加到 0.18 让填充更醒目，避免「看起来在节点后面」的错觉。
- **mouseup 自带 clientX/Y**：原代码 `curX/curY` 依赖最后一次 `mousemove`，但真实浏览器里 mousemove 可能晚于 mouseup 到达（事件队列竞争），导致 `__lastSelRect` 停在中间帧。改为 `onUp` 接 `(e?: MouseEvent)`，用 `e.clientX/Y` 作为终点，curX/curY 兜底。
- **correctBoxSelection 改纯屏幕坐标**：原 canvas 坐标比对要把节点 `getBoundingClientRect` 反变换回画布（手动解析 `translate(...) scale(...)`），任一项读错都会漏选。改为全 CSS px 坐标系：`__lastSelRect.screenLeft/Top/Right/Bottom` 直接与节点 `getBoundingClientRect()` 比较；viewport 缩放时两边同步，结果一致；零 transform 数学。
- **E2E 保持 15/15 PASS**。

## 节点编辑框光标位置修复（刷新/打开节点后光标停在开头）
- **用户反馈**：刷新或打开节点后，编辑框已还原内容，但光标停在**第一个位置（开头）**，用户继续输入会插到最前面；期望停在**文本末尾**。
- **根因**：还原内容有两条路径，原都没把光标放到末尾：
  1. 首次挂载（刷新后重开/首次打开有内容的节点）：走 `NodePromptInput` 的 `didInit` effect（`editor.innerHTML = xxx`），不设光标 → 浏览器默认落到开头。
  2. 切换节点（编辑器已挂载）：走 `setHtml` 命令式方法（`editor.innerHTML = xxx`），原也不设光标。
  - 注意：`setHtml` 在节点切换 effect 里调用时，`inputRef` 往往还没挂上（输入栏 portal 要等 `anchorEl` 设置后才渲染），所以首挂载场景其实只走了 `didInit`，`setHtml` 是空操作——这也是只修 `setHtml` 不够的原因。
- **修复**：新增 `placeCaretAtEnd(el)` 辅助（focus + `Range.selectNodeContents` + `collapse(false)` 折叠到末尾 + 写入 `window.getSelection`）。在 **两条路径都调用**：① `didInit` 末尾 `if (init) placeCaretAtEnd(editor)`（空新节点不抢焦点，沿用原 setTimeout focus）；② `setHtml` 写内容后立即调用。
- **验证**：`verify/verify_node_media_fixes.py` 新增断言「刷新后打开节点光标停在文本末尾」→ `offset=10,total=10` PASS；原 4 项修复无回退，全部 ✅（图片刷新按钮可用 / 视频刷新内容恢复 / 视频缩略图 video 元素 / 删线移除）。
- 关键坑记录：**内容还原必须同时处理 `didInit` 与 `setHtml` 两条路径**，且输入栏 portal 挂载时序导致首挂载时 `setHtml` 不可达——只修 `setHtml` 会漏掉最常见的刷新场景。

## 节点编辑框「点击任意位置光标都落开头」修复（用户又报：输入位置永远在第一个位置）
- **用户反馈**：编辑框（节点提示词输入框）每次点开/点击内部，鼠标输入位置永远在第一个位置（开头），不管有没有内容。即点击中段也应把光标放到点击处。
- **根因**：`contentEditable` 编辑器内含 `@` 引用图/视频 token（`contenteditable=false` 的 `pea-ref` 非可编辑 span）。WebKit/Blink 在含这类非可编辑 token 的编辑区里，点击邻近 token 的文本时浏览器默认会把 caret 落到该文本节点的 offset 0（而不是真实点击点）；叠加 `NodeChatPrompt` 频繁 re-render 的选择回填时序竞争，偶尔也把 caret 推回 0。
- **修复**（`NodePromptInput.tsx`）：新增 `placeCaretFromPoint(clientX, clientY)`——用 `document.caretPositionFromPoint(x,y)`（旧 Safari 回退 `document.caretRangeFromPoint`）从真实屏幕坐标反算点击落点，与当前 selection 一致则 no-op，不一致则显式 `setSelection` 覆盖。注意必须**直接以 `document` 为 this 调用**（解构成独立 `const fn` 会丢 this 抛 "Illegal invocation"）。`pea-ref` token 内部（offsetNode 带 `data-pea-ref=1`）不作为落点，默认放 token 之后（`parent.childNodes` 中 idx+1）。新 `handleMouseUp` 仅在编辑器内点击时调用它；编辑器 div 加 `onMouseUp={handleMouseUp}`（原有 `onMouseDown` 仍 `stopPropagation`）。
- **验证**：`verify/verify_prompt_caret_fix.py` **5/5 PASS**（点 t1 右→"穿到"@0、点 t2 左→"穿到"@2、点开头→"把"@0、点结尾→"模特身上"@4、连点 3 次→末位 @4）；`verify_group_box_fixes.py` 回归 **15/15 PASS**。headless 未复现"永远 offset 0"原症状（与 IME/真实浏览器时序相关），但修复为防御式且已验证点哪到哪。
