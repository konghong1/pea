## 1. 状态字典（团队统一口径）

每个任务维护 **3 个独立状态维度**。三者不互相推导——一个任务可以"开发完成"但"测试有缺陷"且"暂不上线"。

### 1.1 开发状态（Dev Status）
| 值 | 含义 | 进入下一状态的条件 |
|---|---|---|
| `未开始` | 尚未排期/认领 | 已认领且开始写码 |
| `设计中` | 方案/接口/数据模型评审中 | 设计评审通过、可写码 |
| `开发中` | 正在写码 | 自测通过、提 MR |
| `待联调` | 代码完成，等前端/后端/Worker 联调 | 联调通过 |
| `开发完成` | 功能自测通过、已合入主干 | 测试状态进入"测试中" |
| `搁置` | 本期不做（如电商套图 M2，用户 2026-07-22 决定延后） | 重新启用需用户确认并评估依赖链 |

### 1.2 测试状态（Test Status）
| 值 | 含义 |
|---|---|
| `未测试` | 尚未测试 |
| `自测中` | 开发本人自测 |
| `测试中` | QA 按验收标准执行 |
| `测试通过` | 全部验收标准（AC）通过，无遗留阻塞缺陷 |
| `有缺陷` | 存在未关闭缺陷（在"备注/缺陷号"列标注缺陷 ID 与数量） |

### 1.3 上线状态（Release Status）
| 值 | 含义 | 晋级条件 |
|---|---|---|
| `阻塞` | 依赖未就绪 / 有关键缺陷 / 缺配置 | 依赖绿 + 测试通过 + 有回滚方案 |
| `可灰度` | 可小流量/内部验证 | 灰度无异常 + 监控无告警 |
| `可全量` | 可全量发布 | 灰度达标 |
| `已上线` | 已发布生产 | 运维确认 + 监控稳定 |

### 1.4 其余字段
- **优先级**：`P0`（Now 必须）/ `P1`（Next/Later）。
- **依赖（Depends）**：填**前置任务 ID**；所有依赖为`开发完成`且`测试通过`后方可认领。
- **负责人**：人名/角色（空 = 未分配）。
- **备注/缺陷号**：放联调问题、缺陷 tracker ID、决策待确认项。

## 4. 任务明细（描述 + 验收标准 + 依赖）

> 验收标准对齐 PRD 的 FR 编号 / 架构章节；开发完成需**逐条可演示或自动化验证**。

### E0 基础工程与部署基座
- **T-INFRA-01 本地一键环境**：docker-compose 起 MySQL 8 + Redis + 本地 S3 兼容(minio) + CDN mock；`make up` 一把起。**AC**：新人有文档 5 分钟内起全栈；MySQL/Redis 可连。
- **T-INFRA-02 MySQL Schema 初始化**：核心表 DDL（users/accounts/ledger_entries/canvases/canvas_versions/generation_jobs/generation_plans/products/product_images/works），含 JSON 列、生成列索引、ledger 按月分区、accounts.version 乐观锁。**AC**：脚本可重复执行（幂等）；DESIGN §容量表结构落地。**依赖**：T-INFRA-01。
- **T-INFRA-03 仓库骨架**：`pea-server/`（web/ + services/bff + services/generation-orchestrator + services/shared + infra/docker|k8s|mysql/init + README 指向 ../pea）。**AC**：目录即架构 §6；README 说明模块边界与启动。
- **T-INFRA-04 CI 流水线**：lint/build/单测/镜像构建；主干保护 + MR 模板。**AC**：push 触发；失败阻断合并。
- **T-INFRA-05 可观测基座**：OTel SDK + Prometheus + Grafana 基础看板（请求/QPS/队列深度/生成耗时）。**AC**：一个生成任务可全程 trace。**依赖**：T-INFRA-01。

### E1 账户与积分（重心依赖）
- **T-ACC-01 注册登录**：BFF NestJS 鉴权模块，JWT 签发/校验，密码哈希。**AC**：登录返回 token；受保护接口无 token 拒。**依赖**：T-INFRA-02。
- **T-ACC-02 积分钱包**：accounts 表 + 余额查询接口（PRD FR-G2 来源）。**AC**：返回当前余额；顶栏可展示。**依赖**：T-ACC-01。
- **T-ACC-03 双记账本**：ledger_entries 预扣/确认/退还事务（行锁 + `txn_id` 唯一幂等）；余额在事务内强一致更新（架构 D12）。**AC**：预扣成功余额减；生成失败退还余额回；重复 `txn_id` 不双扣。**依赖**：T-ACC-02。
- **T-ACC-04 余额缓存与对账**：Redis Cache-Aside + 单飞；每日对账脚本比对 ledger 汇总与 balance（DESIGN §积分）。**AC**：缓存失效后回源一致；对账脚本报告差异。**依赖**：T-ACC-03。
- **T-ACC-05 积分流水账单接口**：PRD FR-G3 列表/分页。**AC**：可按用户/时间查流水。

### E2 生成管道核心 ★（系统重心）
- **T-GEN-01 任务表与状态机**：generation_jobs（status：queued→running→done/failed→refunded）；`idempotency_key` 防重。**AC**：状态合法流转；非法跳转被拒。**依赖**：T-INFRA-02。
- **T-GEN-02 BFF 受理接口**：校验 + 预扣积分（调 T-ACC-03）+ 写 job + 返 jobId，p95<2s。**AC**：返回 jobId；积分不足返回明确错误（PRD FR-G2）。**依赖**：T-GEN-01,T-ACC-03。
- **T-GEN-03 队列与护栏**：Redis Streams 队列 + 优先级(极速/普通) + 每用户限流 + Provider 预算/断路器（架构风险 R1/R2）。**AC**：超限任务排队/拒；某 Provider 熔断不影响其他。
- **T-GEN-04 FastAPI Worker**：消费队列 → 调外部模型。
- **T-GEN-05 LiteLLM 路由层**：统一接入外部大模型（图/视频/LLM），限流/成本/自动回退（架构 D5）。**AC**：主 Provider 失败自动切备用；记录成本。**依赖**：T-GEN-04。
- **T-GEN-06 回写与推送**：Worker 回写 job 状态 + 媒体落 S3（T-FILE-02）+ BFF 经 WS/SSE 推进度/结果。**AC**：前端实时收到 done+URL。**依赖**：T-GEN-04,T-INFRA-01。

## 5. 从哪接活（接手决策指南）

按此顺序判断，避免"拿了一个上游还没好的任务干半天"：

1. **看依赖是否全绿**：在 §3 矩阵里，找到你感兴趣的任务，检查其 `依赖` 列所有任务是否 `测试通过`（至少 `开发完成`）。有任一未达标 → **先别认领**，去认领那个未达标的前置任务。
2. **认领条件**：`开发状态=未开始` + 依赖全绿 + 有空闲产能 → 改为`设计中`，在任务明细里确认验收标准，再转`开发中`。
3. **卡点定位（谁在挡路）**：
   - 大片 `阻塞` 在 E0/E1/E2 → 重心线没通，优先 E0→E1→E2。
   - `待联调` 多 → 前后端/Worker 接口对不齐，开联调会，对照任务明细的接口契约。
   - `有缺陷` → 看"备注/缺陷号"，缺陷 owner 优先修；阻塞级缺陷不晋级上线。
4. **晋级上线**：`测试通过` + 缺陷清零 + 有回滚方案 → `可灰度` → 灰度无异常 → `可全量` → `已上线`。
5. **进度快照**：每周用 §3 矩阵统计各 Epic 的"开发完成/测试通过/可全量"计数，对照 §2 里程碑门判断是否到 Gate。
6. **⏸ 电商套图 M2（E6）本期搁置**：T-M2-01~08 全部标记`搁置`，不排入 Now 迭代；其下游 T-OBS-02（E2E）暂仅覆盖 M1 生成链路，M2 部分待解封后补。重新启用 M2 前需用户确认，并重新评估依赖链（E4 文件存储仍保留——M1/M5 等也依赖它，不随 M2 搁置）。
