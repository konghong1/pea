---

## 0. 这份路线图怎么用

- **对齐关系**：本图以 PRD §14 的 `Now / Next / Later` 为骨架，把每个阶段**展开成可排期、可验收、可追责**的版本计划；架构动作直接引用 `ARCH 终稿 §8` 与 `ARCH 终稿 §1` 的演进策略。
- **时间锚点**：以 `M0 = 2026-07（项目启动月）` 为相对起点。日历日期为**示意**，正式排期在 kickoff 时按团队规模/云资源就绪度 re-baseline。
- **演进纪律**：每一阶段结束必须达成该阶段的 **DoD（退出标准）** 才能进入下一阶段。架构抽服务只看 `ARCH 终稿 §1` 的三条触发条件，不按"感觉该拆了"拆。
- **诚实声明**：原型阶段所有"生成"为前端模拟，因此 **Now 阶段的最大不确定性是"真实生成服务能否按时可用"**，路线图把它列为贯穿 Now/Next 的阻塞依赖。

## 2. 阶段详设 — NOW（M0–M3，MVP / 端到端打通）

### 2.1 业务目标
让一个**真实用户**走完"上传产品图 → AI 策划 → 一键生成 → 画布看到产出 → 消耗积分"的完整链路，证明核心假设（AI 套图 + 画布编排能创造价值）。

### 2.2 范围（对齐 PRD）
| 模块 | 本阶段交付 | 对应 PRD |
|---|---|---|
| **G 全局** | 顶栏导航、账户/积分骨架、AI Provider 配置持久化、Toast | §5 |
| **M1 画布（基础）** | 节点/连线/缩放平移/小地图/Inspector/Agent 入口；**自动保存（P0）** | §6.1–6.2.6, 6.2.7 入口 |
| **M2 电商套图（配置+生成）** | 上传/卖点/市场/输出/AI 策划台/规划/属性弹窗/生成流程 | §7 |
| **M5 账户（骨架）** | 资料、AI Provider、积分展示入口（支付仅入口） | §10 骨架 |

> 本阶段**不做**：M1 完整交互（右键/快捷键/侧边面板/节点库 → Next）、M3 主页、M4 社区、协作、支付真实接入。

### 2.3 架构演进动作（对齐 ARCH 终稿 §1/§8）
- 单仓 / 单部署 **模块化单体**：以 module/package 边界区分 `identity / canvas / generation / ecommerce / billing` 五大上下文（ARCH 终稿 §2）。
- 主库 **MySQL 8**（JSON 列存画布节点图与出图规划），**Redis**（会话/限流/实时 PubSub）。
- 生成侧落地 **Python FastAPI + 队列（Temporal 或 Celery）Work第一次**，同步 API 仅"受理+预扣积分+返回 jobId"（ARCH 终稿 §5.2，ADR-002）。
- 前端 **React + React Flow + Zustand + Tailwind**（替代原型原生 JS 全量重建，ARCH 终稿 §4.1 / ADR-003）。
- 画布**自动保存**上线（debounce ~1s + 失焦即存，ARCH 终稿 §5.1），直接解决 PRD 标红的"刷新即丢"痛点。
- **积分双记账本**最小实现（预扣 + 失败补偿），ACH 核心不变量（ARCH 终稿 §5.4 / ADR-006）。

### 2.4 关键交付物
1. 可演示环境：一个创作者账号，从零走通端到端。
2. 画布 MVP（基础节点操作 + Agent 入口）。
3. 电商套图生成（真实调用 1–2 个 Provider，如 MJ/Kling）。
4. 积分预扣 + 账单流水（最小可审计）。
5. 自动保存（用户无感，刷新不丢）。

### 2.5 成功指标（对齐 PRD §2，Now 基线）
- 端到端生成任务创建响应 < 2s；生成成功率（非演示）≥ 90%（Now 允许略低于 95% 目标）。
- 画布 ≤50 节点 ≥60fps（PRD NFR）。
- 至少 **1 个内部试点用户** 完成 ≥1 套电商套图生成。
- 北极星指标开始采集（周活跃有效创作产出数）。

### 2.6 退出标准（DoD）
- [ ] 端到端链路在 staging 跑通，非模拟。
- [ ] 自动保存通过"刷新不丢"验收（AC 类）。
- [ ] 积分无错账（预扣/补偿单测 + 手动对账通过）。
- [ ] 画布基础交互 AC-M1-01~08 中 P0 子集通过。
- [ ] 生成服务可用性 ≥ 约定 SLA（需后端确认，见 §7 依赖）。

### 2.7 团队 / 资源
- 前端 2–3（React/TS）、后端 2（Node BFF + Python 生成）、1 设计、0.5 测试、1 PM/Arch 兼任。
- 云资源：1 MySQL、1 Redis、GPU worker 最小池（按模型需求）。

### 2.8 主要风险与缓解
| 风险 | 影响 | 缓解 |
|---|---|---|
| 真实生成服务未就绪 | 阻塞 M1/M2 生成 | 先用 1 个稳定 Provider 打通；定义清晰集成契约（PRD §11）|
| React Flow 迁移成本 | 进度延迟 | 先小步验证节点/连线，再扩展 |
| 积分错账 | 用户信任崩塌 | 双记账本 + 每日对账 job 早做 |

## 3. 阶段详设 — NEXT（M4–M9，内部可用 Beta）

### 3.1 业务目标
把 Now 的"能演示"变成"**团队内部日常可用**"：画布完整交互、主页入口、账户完整、自动保存稳定，进入内部 Beta 征集反馈。

### 3.2 范围（对齐 PRD）
| 模块 | 本阶段交付 | 对应 PRD |
|---|---|---|
| **M1 画布（完整）** | 右键菜单、快捷键、侧边面板（搜索/评论/历史/文件）、节点库、文本富文本工具条、Agent 完整对话 | §6.2.5, 6.2.8, 6.2.9, 6.2.7 完整 |
| **M3 主页 Workspace** | 创作 Agent 入口、项目列表、精选推荐 | §8 |
| **M5 账户（完整）** | 通知偏好、邀请、订阅/账单入口、帮助 | §10 完整 |
| **G** | 自动保存稳定、通知中心、分享、Promotion | §5 |

> 本阶段**不做**：M4 社区公域、竞技场、真实支付、协作、移动端优化。

### 3.3 架构演进动作（对齐 ARCH 终稿 §8）
- **抽离 Generation Orchestrator 为独立服务**（触发条件：GPU 密集型负载与其他上下文显著不同，ARCH 终稿 §1）。
- 引入 **Temporal** 承载长时多步工作流（重试/补偿/断点续跑，ARCH 终稿 §4.2 / §5.2）。
- `community` / `billing` 作为独立 **module** 从单体剥离边界（为 Later 微服务化铺路）。
- **WebSocket 实时化**：Agent 流式 + 任务状态推送（ARCH 终稿 §5/ADR-007），替代轮询。
- **Provider 回退 + 限流 + 预算** 在路由层统一（LiteLLM，ARCH 终稿 §5.3 / ADR-004），防止单用户打爆成本。

### 3.4 关键交付物
1. 画布完整交互版（对标原型全部交互）。
2. 主页 Workspace（项目中枢）。
3. 账户中心完整（含通知/邀请/订阅入口）。
4. 生成服务独立部署、可独立扩缩容。
5. 实时通道（Agent 流式 + 状态推送）。

### 3.5 成功指标（对齐 PRD §2）
- 画布新建率 ≥ 40%（7 日新用户）；Agent 对话激活率 ≥ 55%。
- 生成成功率 ≥ 95%；积分异常率告警可用。
- 内部 Beta 日活（内部）≥ 约定基数；有效创作产出数周环比上升。
- P95 画布首屏 ≤ 1.2s。

### 3.6 退出标准（DoD）
- [ ] M1 全部 AC-M1-01~08 通过；M3/M5 AC 通过。
- [ ] 生成服务独立部署且可水平扩容（压测达标）。
- [ ] 实时通道在弱网下可重连、不丢消息。
- [ ] 成本控制：单用户单日花费有上限 + 告警。

### 3.7 团队 / 资源
- 新增 1 平台/DevOps（K8s + 可观测）、生成服务独立 ownership（1 后端）。
- 引入 OTel/Prometheus/Grafana 全链路可观测（ARCH 终稿 §4.4）。

### 3.8 主要风险与缓解
| 风险 | 影响 | 缓解 |
|---|---|---|
| 编排复杂度（Temporal 学习曲线）| 进度 | 先小范围落地一个 worker，再扩展 |
| 成本失控 | 毛利为负 | 预算上限 + 断路器 + 配额，EARLY |
| 单体边界被腐蚀 | 将来难拆 | 严格依赖方向（内层不依赖外层），Code Review 守门 |

## 4. 阶段详设 — LATER（M10–M18，公测与增长）

### 4.1 业务目标
面向**公域用户**公测与增长：社区（TapTV）上线、竞技场、真实支付、移动端适配，开始规模化获客与变现。

### 4.2 范围（对齐 PRD）
| 模块 | 本阶段交付 | 对应 PRD |
|---|---|---|
| **M4 TapTV 社区** | 探索 Feed、创作过程详情、发布（画布产出→社区条目） | §9 |
| **竞技场（Arena）** | 导航占位 → 真实功能（PRD 原 Non-Goal，本阶段补） | §4.2 |
| **支付接入** | 订阅/充值真实收银台（PRD 原 Non-Goal，本阶段补） | §4.2 |
| **协作（单人→多人）** | 实时协同光标/同步（PRD 原 Non-Goal，本阶段补） | §4.2 |
| **移动端适配** | 响应式优化（非原生 App） | §4.2 |
| **G** | 多区域数据驻留预备 | §9 风险 |

### 4.3 架构演进动作（对齐 ARCH 终稿 §8）
- **限界上下文微服务化**：按 ARCH 终稿 §2 五大上下文 + Billing/Notification 拆独立服务，K8s 按域部署。
- **实时协作**引入 **Yjs (CRDT) + WS 广播**，多光标（ARCH 终稿 §4.1 / §5.1）。
- **向量检索**（Qdrant / MeiliSearch）支撑画布/社区搜索、参考图语义匹配（ARCH 终稿 §4）。
- **弹性 GPU 调度**：按模型类型独立节点池（image/video/audio/3D），K8s 弹性扩缩。
- **多区域 / 数据驻留**：解决跨境（北美/欧洲）合规（ARCH 终稿 §9 风险 5）。

### 4.4 关键交付物
1. TapTV 公域社区（UGC + 推荐）。
2. 真实支付（订阅/充值/账单）。
3. 多人实时协作画布。
4. 微服务化架构，各域独立部署/扩缩。
5. 移动端可用适配。

### 4.5 成功指标（对齐 PRD §2）
- TapTV 发布率 ≥ 15%；电商套图生成转化率 ≥ 30%。
- 公测 MAU / 留存达增长目标。
- 付费转化率、ARPU 达商业目标（需真实定价，见 §7 待对齐）。

### 4.6 退出标准（DoD）
- [ ] M4 AC-M4-01~02 通过；支付端到端（下单→回调→到账→开票）跑通。
- [ ] 协作冲突解决正确（CRDT 收敛测试）。
- [ ] 微服务间无强耦合事务（最终一致可接受）。
- [ ] 多区域合规通过安全评审。

### 4.7 团队 / 资源
- 社区/增长 1 后端 + 1 前端；支付/合规 0.5；协作 1 前端 + 1 后端。
- SRE 强化（多区域、GPU 弹性）。

### 4.8 主要风险与缓解
| 风险 | 影响 | 缓解 |
|---|---|---|
| 分布式复杂度（事务/调试）| 稳定性 | 严格限界上下文 + 事件驱动 + 对账 |
| 协作冲突/性能 | 体验 | CRDT 早验证；先小团队试点 |
| 合规/数据主权 | 法律风险 | 多区域架构前置设计，别事后补 |
| 媒体存储成本 | 毛利 | 生命周期（N 天降冷/清理）+ CDN（ARCH 终稿 §9 风险 2）|

## 5. 远期愿景（VISION，18+ 月）

> 不在排期内，作为方向锚，防止"为扩张而扩张"。

- **平台化**：开放画布节点 SDK / 第三方 Provider 市场，开发者贡献节点与模型。
- **Agent 生态**：用户可训练/发布专属创作 Agent，形成市场。
- **企业版**：团队空间、权限、审计、SSO、私有化部署。
- **多模态创作中台**：图像/视频/音频/3D 统一编排，成为创作者基础设施。
- **AI 成本自治**：基于用量预测的弹性预算与自动选型，毛利可预测。

## 6. 跨阶段技术主线（演进不回头）

| 主线 | Now | Next | Later | Vision |
|---|---|---|---|---|
| 生成架构 | 单体内 Worker | 独立 Orchestrator + Temporal | 微服务 + 弹性 GPU 池 | Provider 市场 |
| 数据 | MySQL+Redis | + 事件总线 | + 向量检索(Qdrant) | 多区域副本 |
| 实时 | 轮询/WS 试点 | WS 实时化 | CRDT 协作 | 边缘协同 |
| 一致性 | 强一致（钱包）| + 对账 job | 最终一致（社区/通知）| 全局 Saga |
| 成本治理 | 预扣+补偿 | 限流+预算+回退 | 弹性+预测 | 自治选型 |

**演化纪律（不可破）**：
1. 抽服务只看 ARCH 终稿 §1 三条触发条件，不看"觉得该拆"。
2. 每个阶段 DoD 不达标不进下一阶段。
3. 强一致边界（钱包/账单）绝不因"微服务潮流"降级为最终一致。

## 7. 决策门（Go / No-Go Gates）与前提

| 决策门 | 时间锚 | 评审内容 | Go 条件 |
|---|---|---|---|
| **Gate 0：Kickoff** | M0 | 团队/云资源/PRD 优先级对齐 | §8 待对齐项有结论 |
| **Gate 1：Now→Next** | M3 | 端到端跑通 + DoD | §2.6 全过 |
| **Gate 2：Next→Later** | M9 | Beta 指标 + 成本可控 | §3.6 全过 + 毛利模型成立 |

**前提 / 待对齐（呼应 PRD §13，必须在 Gate 0 前拍板）**：
1. 模块优先级是否仍 P0(M1/M2) > P1(M3/M4/M5)？
2. 电商套图积分单价（原型 10/张）最终定价？真实支付何时接？
3. 画布是否需多人协作？本版按单人，协作进 Later。
4. Agent 规则引擎兜底是否可接受，还是全走 LLM？
5. 自动保存 SLA（离线编辑）要求？

## 8. 组织与团队演进

| 阶段 | 团队形态 | 关键角色 |
|---|---|---|
| Now | 单产品小队（全栈为主）| PM/Arch 兼任、2FE+2BE+1Design |

> 架构随组织长大，但**不预先为"未来组织"过度设计**。模块边界先行，组织再跟上。

## 9. 度量与回顾机制

- **季度 OKR 对齐**：北极星（周活跃有效创作产出数）+ 驱动指标（PRD §2）作为公司级 KR。
- **架构健康度**：每月 review 模块耦合度、服务拆分触发条件命中情况、成本/毛利。
- **回顾节奏**：每阶段结束做复盘（What worked / 技术债 / 下一阶段风险）。
- **决策追溯**：所有架构决策进 ADR（ARCH 终稿 §6 模板），Gate 评审时回看。
