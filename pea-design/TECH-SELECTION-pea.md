# 技术选型说明（pea Creative OS）

> 配套文档：`ARCH-pea-Final.md`（架构终稿）、`PRD-pea-Creative-OS.md`（需求）、`ROADMAP-pea-Creative-OS.md`（路线图）、`DESIGN-Core-Subsystems-100k.md`（核心子系统）。
> 本文目标：把每一层技术选型**讲清楚为什么选、替代项是什么、放弃了什么**；并专门回答"为什么不用 MySQL"。

---

## 0. 选型原则（先定规矩，再选技术）

| 原则 | 含义 |
|---|---|
| 演进式、可逆 | 模块化单体起步，抽服务有触发条件；每个选型尽量"换得起" |
| 团队可维护优先 | 不为"技术先进性"牺牲团队能 hold 住的能力 |
| 数据模型驱动 | 先想清楚数据长什么样，再选能最好承载它的存储 |
| 10 万用户容量基线 | 不按百万/千万过度设计，但关键路径留弹性 |

> ⚠️ 一个必须摊开说的事实：**你们现有 AI Agent 系统是 MySQL 栈**（FastAPI + SQLAlchemy + PyMySQL + MySQL）。所以"选 PostgreSQL 还是 MySQL"不是纯技术问题，是**产品数据模型契合度 vs 团队既有运维经验**的取舍。详见 §3。

## 1. 前端层

### 1.1 React 18 + TypeScript
- **为什么**：组件生态最全、招聘面最广、与现有 React + Vite + antd 前端栈一致（你们 AI Agent 前端就是 React + Vite + antd v5），团队已有肌肉记忆。
- **替代**：Vue 3（国内生态好，但节点画布生态弱）、Svelte（性能佳但生态小，招人难）、Angular（太重，迭代慢）。
- **放弃**：自研框架 / 小众框架的"性能红利"，换来更稳的招聘与可维护性。

### 1.2 React Flow（节点画布引擎）
- **为什么**：直接解决 PRD 里"原型全量重建 DOM 掉帧"的坑。它内置节点/连线/缩放/平移/小地图/拖拽，且支持虚拟化和自定义节点。
- **替代**：tldraw（更偏白板、节点连线非强项）、自研 Canvas/SVG（可控但工作量巨大、易踩性能坑）、Rete.js（偏可视化编程，画布交互体验一般）。
- **放弃**：完全自研的"绝对控制"，换来数月工期和一堆性能负债。
- **权衡**：React Flow 在超大规模（>2000 节点）仍需手动优化，但 10 万用户量级下画布规模远不到此阈值。

### 1.3 Zustand（前端状态管理）
- **为什么**：轻量、无 Provider 嵌套地狱、与 React Flow 的 store 模式契合；画布状态/选中态/Inspector 状态用它最干净。
- **替代**：Redux Toolkit（规范但样板代码多）、MobX（响应式强但调试黑盒）、Context 裸用（大状态必卡）。
- **放弃**：Redux 的"强规范带来的可预测性"，换来更低的样板成本（画布编辑器状态变化极频繁，Redux 样板会拖慢迭代）。

### 1.4 Tailwind CSS + antd v5
- **为什么**：Tailwind 做高保真、强定制的创意类 UI 效率极高；antd 提供现成表单/弹窗/表格等中后台组件（你们已用 antd v5）。两者可共存：antd 管标准控件，Tailwind 管画布/卡片等定制区。
- **替代**：纯 antd（定制画布类 UI 受限）、纯 CSS-in-JS（无原子类快）、纯 Tailwind（中后台表单重复造轮子）。
- **注意**：需统一设计 token，避免两套样式体系打架。

### 1.5 Vite（构建）
- **为什么**：快（HMR 秒级）、配置轻；你们前端已用 Vite。
- **替代**：Webpack（生态老但慢）、Next.js（若需 SSR/SEO 才上，本产品是重交互 SPA，SSR 收益低）。
- **放弃**：SSR/SEO 能力（创意工作台不需要搜索引擎收录）。

## 2. 后端 / 服务层

### 2.1 Node.js + NestJS（BFF / API 网关）
- **角色**：前端聚合层、鉴权、限流、WebSocket/SSE 推送、文件预签名。
- **为什么**：与前端同语言（TS），减少上下文切换；NestJS 模块化 + 依赖注入，适合长期演进；天然支持 WebSocket（画布协作、生成进度推送）。
- **替代**：纯 FastAPI 做 BFF（你们 Python 强，但前端聚合用 TS 更顺、WS 生态更熟）、Express/Koa 裸写（灵活但缺结构，规模化易乱）。
- **放弃**："全 Python 栈"的统一性，换来前后端协同效率（BFF 离前端最近，TS 端到端类型共享价值高）。

### 2.2 Python + FastAPI（生成编排服务）
- **角色**：AI 生成的核心——调模型、多步工作流、Worker。
- **为什么**：AI/ML SDK 生态最佳（PyTorch、各类模型 SDK、LiteLLM 都是 Python 优先）；FastAPI 异步性能好、类型友好。
- **替代**：Node 调 AI（可行但 ML 生态弱一截）、Go（性能强但 AI 库少、开发慢）。
- **放弃**：单一语言栈的纯粹性，换来 AI 生态的可用性（这是产品核心，不能省）。

### 2.3 生成编排：Temporal vs Celery（重点权衡）
- **Temporal**：工作流即代码，自带**重试、补偿（Saga）、超时、心跳、可观测、断点续跑**。非常适合"多步 AI 生成 + 失败退还积分"这种长事务。
  - 代价：引入 Temporal Server（运维成本）、概念较重、团队需学习。
- **Celery + Redis/RabbitMQ**：轻、团队熟、上手快。
  - 代价：重试/补偿/超时需自己写，长事务易出错，可观测弱。
- **建议（10 万用户）**：**Now 阶段用 Celery + 消息队列快速跑通**；**Next 阶段迁移 Temporal**，因为"生成失败要精确退还积分"这种 Sagas 逻辑，Celery 手写会越来越脆。Temporal 是把"可靠性"从"靠人写对"变成"框架保障"。
- **放弃**：Now 阶段的"一步到位"，换来更快 MVP；但前期就用幂等键 + 事件补偿打底，迁移 Temporal 时改动可控。

### 2.4 LiteLLM（AI Provider 路由）
- **为什么**：统一接入 Midjourney / Kling / OpenAI / 自建模型等，**统一鉴权、限流、成本统计、自动 fallback**。直接对应 PRD 里"AI Provider 配置 + 回退"。
- **替代**：自研适配层（每个 Provider 写一套，维护成本高、易漏边界）、直接各 SDK 混用（无统一限流/成本视图）。
- **放弃**：对各 Provider 的"极致定制控制"，换来统一的限流/成本/回退护栏（成本失控是头号风险，见 ROADMAP R1）。

## 3. 数据层（含"为什么不用 MySQL"）

### 3.1 主数据库：MySQL 8（已锁定）
**决策结论**：在 10 万用户量级 **MySQL 完全能扛住规模**；经权衡本产品**锁定 MySQL 8**（复用团队既有 MySQL 栈与运维经验），画布/规划用 JSON 列 + 生成列索引，向量检索后期独立上 **Qdrant**。下方保留当时的选型权衡供参考。

#### PostgreSQL vs MySQL 选型权衡（曾倾向 PG，最终锁定 MySQL）
| 维度 | PostgreSQL | MySQL 8 |
|---|---|---|
| **灵活结构（画布/生成规划）** | `JSONB` + GIN 索引 + 丰富算子（`@>` 包含、`?` 存在、`jsonb_path_query`），可对 JSON 内部字段建索引、做 containment 查询 | 有 JSON 类型 + 多值索引（生成列），但算子/索引能力弱一截，复杂 JSON 查询要吃力些 |
| **向量检索（后期必做）** | `pgvector` **原生同库**，AI 创意产品的"以图搜图/相似 prompt/社区相似内容"直接一个库搞定 | 需**外接 Qdrant / Milvus**，等于多维护一套系统 |
| **社交/分析 SQL** | CTE、递归查询、窗口函数强；社区 feed、评论树、关注图、排行榜写起来顺 | 8.0 已改善，但递归/复杂分析仍不如 PG 顺手 |
| **一致性** | 默认 READ COMMITTED 稳健，支持 SERIALIZABLE；行锁/双记账本可靠 | 默认 REPEATABLE READ，DECIMAL 精确、行锁同样可靠 |
| **双记账本** | 完全胜任（DECIMAL + 事务 + 行锁） | 同样胜任 |

#### 但 MySQL 有三个真实优势，我必须承认
1. **你们已经在用**：AI Agent 系统就是 MySQL 栈，团队有运维和排障经验——这是非常大的隐性资产。
2. **简单读扩展更成熟**：读副本、组复制在超高 QPS 简单读场景下更顺，连接模型（线程/连接）在海量短连接下更稳。
3. **生态惯性**：现有 SQLAlchemy 模型、备份脚本、监控可直接复用。

#### 所以真正的问题是：你要"一个库搞定"还是"两个库但更熟"？
- **路径 A（原建议）：PostgreSQL 单主库**
  - 优点：JSONB（画布/规划灵活演进，少做 migration）+ pgvector（后期 AI 检索同库）+ 强分析 SQL，**运维面最小（一套关系库 + 缓存 + 对象存储）**。
  - 代价：团队需补 PostgreSQL 运维经验（你们 MySQL 熟，但 PG 上手不难，且有云托管 RDS 兜底）。
- **路径 B（完全可行）：MySQL + Qdrant（向量）**
  - 优点：**复用你们既有 MySQL 经验与脚本**，读扩展更顺。
  - 代价：后期 AI 检索要单独养一套 Qdrant；画布 JSON 查询不如 JSONB 顺。
- **路径 C（折中，不推荐初期）**：MySQL 存核心 + PostgreSQL 存画布/向量。两套关系库，运维面翻倍，10 万用户阶段不值得。

> **最终决策（已锁定）**：走**路径 B（MySQL + Qdrant）**——复用团队既有 MySQL 经验与脚本，向量检索交给独立 Qdrant；画布存储采用"JSON 列 + 必要生成列"写法。该决策已在 Gate 0 拍板，换库迁移成本高，后续不再纠结。

### 3.2 Redis（缓存 + 队列 + 限流）
- **为什么**：① 积分余额缓存（Cache-Aside + 单飞）；② 生成任务队列（Redis Streams）或配合 Celery；③ 用户级限流计数器；④ 画布"乐观锁版本号"的轻量校验可借力。
- **替代**：Memcached（纯缓存，无队列/结构）、数据库轮询（慢、压主库）。
- **放弃**：无（Redis 是这类系统的标配）。

### 3.3 对象存储：S3 兼容（MinIO / 云 OSS）
- **为什么**：生成媒体（图片/视频）体量巨大（容量模型：~50TB），块/文件存储不经济；S3 有**预签名直传、CDN 友好、生命周期分层（标准→IA→归档）**直接压成本。
- **替代**：本地磁盘（不可扩展、无 CDN）、NFS（性能与扩展差）。
- **放弃**：无。详见 `DESIGN-Core-Subsystems-100k.md` §文件存储。

### 3.4 向量检索（后期）：Qdrant
- **为什么**：社区"相似作品"、素材"以图搜图"、prompt 复用推荐——AI 创意产品的标配。
- **时序**：Now 阶段不做（MVP 不需要），Next/Later 引入 Qdrant。

## 4. 基础设施层

| 技术 | 用途 | 为什么 | 替代 |
|---|---|---|---|
| Docker + K8s | 容器编排，**GPU worker 独立节点池** | 生成是 GPU 密集型，必须能和 API 分离伸缩 | 裸机（运维痛）、Nomad（小众） |
| CDN | 媒体分发、前端静态资源 | 降低源站压力、提速全球访问 | 直连 OSS（慢、贵） |
| OpenTelemetry + Prometheus + Grafana | 全链路 trace / 指标 / 看板 | 生成管道跨服务，必须能追"一次生成卡哪了" | 各家 APM 锁定 |
| 消息队列 | 生成任务解耦 | 见 §2.3 / 核心子系统文档 | 直接同步调用（会打死线程） |
| 日志聚合（Loki/ELK） | 集中日志 | 排障必需 | 散落文件 |

## 6. 待拍板（Gate 0 前必须定）

1. **主库 PG 还是 MySQL+B 路径**？（本文 §3 的核心决策，影响全部 Schema 设计）
2. **编排 Now 用 Celery 还是直接 Temporal**？（影响生成可靠性代码量）
3. **向量检索（Qdrant）是否纳入 Next 阶段范围**（决定落地节奏）
4. **Redis 是否承担队列**（还是单独 RabbitMQ/SQS）——取决于云环境与运维偏好。

> 一句话总结选型哲学：**前端跟着生态和团队走，后端按"离用户近用 TS、离 AI 近用 Python"分，存储按数据模型选 PG（或你们熟的 MySQL+Qdrant），一切以"团队能长期维护、换得起"为底线。**
